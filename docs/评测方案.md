# 评测方案 · 采集口径

> **原则：口径先定死，再采数。** 三栈共用同一套打点位置、同一套样本集、同一套统计方法，
> 否则数据不可比，结论就是废的。
>
> 采集环境：`<待填开发板型号 / Android 版本 / 麦克风布局 / 采集日期>`

## M1 · 分段延迟分解

### 打点位置

> A 栈锚点已对齐项目真实接口（`SpeechEventManager` 4.8.7.2）的回调常量。
> **回调中禁止阻塞与耗时操作**——打点必须在回调内立即取时间戳，异步处理。

| 时刻 | 定义 | A 栈 · 百度定制版回调锚点 | C 栈 · 自研锚点 |
|---|---|---|---|
| t_a | 用户开口（语音起点） | `CALLBACK_EVENT_ASR_BEGIN` | VAD speech start |
| **t0** | **端点判定成立（用户停止说话）** | **`CALLBACK_EVENT_ASR_END`** | EOU / VAD end |
| t1 | ASR 首个中间结果 | `ASR_PARTIAL`，`result_type = partial_result` 首次 | STT partial |
| t2 | ASR 最终结果 | `ASR_PARTIAL`，`result_type = final_result` | STT final |
| t3 | 语义 / DM 首个可用输出 | `ASR_PARTIAL`，`result_type = third_result`（语义资源结果） | LLM / tool call 首 token |
| t4 | TTS 首个可播 PCM 包 | 合成 SDK 首包回调 | TTS first chunk |
| t5 | 扬声器实际出声 | `AudioTrack` 写入首帧 + 实际播放时戳 | 同 |
| t_w | 唤醒成功时刻 | `CALLBACK_EVENT_WAKEUP_SUCCESS` 的 `wakeup_time` 字段 | 同 |

**派生指标**

```
唤醒响应   = t_a - t_w      唤醒到用户开口（唤醒链路健康度）
说话时长   = t0 - t_a      ★ 端点是否过早/过晚截断的直接证据
端点延迟   = t1 - t0        端点判定到首个识别结果（用户感知最直接的一段）
ASR 完整   = t2 - t0
语义等待   = t3 - t2        理解与生成起效
TTS 首包   = t4 - t3
出声延迟   = t5 - t4        播放器缓冲造成
端到端     = t5 - t0        ★ 核心指标
```

> **"说话时长"这一项常被忽略，但它是端点质量最直接的证据。**
> 用户话没说完就被切（时长偏短）→ 识别必然丢后半句；用户停顿就切（时长偏短且频繁）→ 需调端点参数。

### 关于结束回调的两个坑

| 回调 | 语义 | 什么时候用 |
|---|---|---|
| `CALLBACK_EVENT_ASR_FINISH` | 识别完成，**但后面还有语音资源**；多次交互每次识别结束都有一次 | 交互轮次边界。**离在线并行模式下，离线与在线各回调一次** |
| `CALLBACK_EVENT_ASR_EXIT` | 识别**最终结束**，不区分单次/多次/并行，**全程只有一次** | 会话生命周期终点 |

- **M1 的 t2 用 `final_result`，不要用 `ASR_FINISH`**——后者含语义资源下发，混在一起测不出 ASR 本身。
- 并行模式（`DECODER = 4`）必须按 `engineType`（0 在线 / 1 离线）分别记录，**不能假设只回调一次**。
- `start_end_frames` 字段可回溯语音起止帧，用于校验 t_a / t0 是否合理。

### 三栈 t0 口径一致性（必须处理）

A 栈的 `ASR_END` 来自 DSP 侧端点判定，C 栈的 EOU 来自软件 VAD，**两者语义并不等价**。

两种做法，**必须二选一并在报告中声明**：

1. **统一用外部判定**：在录音输入侧统计"最后一个语音活动帧"，三栈共用同一个外部时间基准（最公平，但需自己实现）。
2. **各栈用各自的 t0**，在报告中单列"端点判定差异"一节，说明 A 栈偏早/偏晚多少毫秒（更真实，但需额外解释）。

> **推荐做法 1。** 做法 2 的数据在面试时会被追问，很难自圆其说。

### 统计方法

- 每档场景 **≥30 次**，剔除首次（冷启动与模型加载）。
- 报 **P50 / P90 / P95 / max**，不要只报均值——语音交互的体验由长尾决定。
- 三栈必须使用**同一批录音文件**输入，不做实时麦克风输入（避免随机性）。
- 百度 A 栈与 C 栈的 t0 判定方式若不同（各自 VAD），必须在报告中注明并单独说明差异影响。

### 必测场景

安静 / 车内中噪 / 车内强噪 / 网络抖动（3G 等效 300ms RTT）/ 断网（仅 C 栈可用）。

## M2 · 噪声 SNR 分档评测

### 噪声档位

| 档 | SNR | 场景 |
|---|---|---|
| S0 | ≥35 dB | 安静/怠速 |
| S1 | 20–30 dB | 城市道路 60–80km/h |
| S2 | 10–20 dB | 高速 100–120km/h、开窗 |
| S3 | ≤10 dB | 强风、雨天、音乐全开 |

### 噪声类型（每档至少覆盖前三类）

风噪 / 路噪与胎噪 / 音乐干扰（流行 + 人声歌）/ 多人同时说话 / 提示音与导航播报。

### 样本集

- 指令集：**≥100 条**，取自真实车控高频指令（开窗、空调、导航、媒体、电话…）。
- 每条在每档噪声下重复 **≥3 次**，报均值与最差 10%。
- 场景库放在 `bench/noise/`，manifest 记录每条样本的 SNR 实测值、噪声类型、采集设备。

### 指标

| 指标 | 定义 | 注意 |
|---|---|---|
| 唤醒率 | 应唤醒次数 / 实际唤醒次数 | 需区分"未唤醒"与"唤醒但识别错" |
| 误唤醒率 | 无人说话时的唤醒次数 / 无人说话时长 | **量产最关心的指标**，单独统计 |
| CER | 字符错误率 | 统一用同一份标准答案文本 |
| 端到端延迟 | 见 M1 | 噪声会显著抬高延迟，需一并记录 |

## M4 · 资源开销

| 指标 | 采集方式 |
|---|---|
| 常驻内存峰值 | `dumpsys meminfo` 采样 PSS，间隔 1s，取峰值 |
| 模型体积 | 磁盘占用 + 运行时加载体积 |
| 包体增量 | APK 体积差值 |
| CPU 占用 | `top` / `dumpsys cpuinfo`，空闲态与活跃态分别采样 |
| 温升 | 连续运行 30 分钟，读取 SoC 温度传感器（`/sys/class/thermal/`） |
| 首帧加载时间 | 冷启动到首包产出的耗时（用户点唤醒到出反应） |
| 功耗 | 电流采样（若板子支持），否则用 CPU 时间 × 电压近似 |

**内存治理铁律**：多模型**串行**执行，峰值内存不叠加。
参考公开实测：4 个小模型串行常驻约 1.1GB；若并行，峰值会翻倍并触发 lowmemorykiller。

### M4.1 · 端侧部署档位对比（C 栈专属，A 栈做参照）

> **为什么要有这一节**：A 栈的降噪跑在**高通 HTP**（8295 / 8155）上，模型由百度提供。
> 你负责集成与问题定位，但**没有做过模型层的转换、量化、算子评估、性能调优**。
> C 栈的部署档位对比，就是你**自己把这条链路完整走一遍**的地方——
> 走完之后，你才具备"能独立完成端侧部署与选型"的能力，而不只是在别人的模型上做集成。

| 档位 | 推理后端 | 前提 | 状态 |
|---|---|---|---|
| **C-1** | ONNX Runtime · CPU | 无依赖，一定能跑 | 必做（基线） |
| **C-2** | ONNX Runtime + NNAPI | Android 系统接口，无需额外 SDK | 必做 |
| **C-3** | QNN / Qualcomm AI Engine Direct（HTP） | 需申请 QNN SDK | 加分（有条件） |
| **A（参照）** | 高通 HTP（百度模型） | 现成方案 | 对照组 |

**C-3 的价值**：把**同一个模型**分别跑在 CPU、NNAPI、HTP 三种后端上，得到一张
「延迟 / 内存 / 功耗 / 温升 / CER」的横向表。这张表同时证明三件事：

1. 你会做模型转换与量化（不只是集成别人的模型）
2. 你能量化不同部署档位的取舍（这正是选型能力）
3. 你能和 A 栈做**同芯片、同工具链**的对比，而不是拿 PC 结果充数

> **注意算子回退**：Conformer 类架构在 NPU 上约有 15% 算子回退 CPU，是延迟抖动主因。
> C-3 一定要记录实际回退比例，这是很难得的实操数据。

## M5 · 选型结论

输出到 `docs/选型结论.md`，一页纸，包含：

1. **一句话结论**（如：强噪车内场景 X 栈不可量产，仅 Y 栈可兜底）
2. **决策表**：按场景给出推荐栈与代价

## 通用纪律

- **每次采集记录批次号**：日期 + 板子 + 固件版本 + 应用 commit。数据没有批次号一律作废。
- **原始数据入 `bench/results/`（CSV），结论入 `docs/`。** 数据和结论必须能相互追溯。
- 任何一格"可用"，都要能在原始数据里找到对应行。
- **如实记录失败**。自研栈在强噪下大概率打不过百度的工程化积累，写明白"何时该用谁"比吹自己强得多。
